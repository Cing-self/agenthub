# 记忆系统

## 1. 为什么记忆是中轴

如果产品目标只是“像聊天机器人一样回复”，那记忆不是中轴。

但 AgentHub 的目标是：

- 持续替用户做事
- 越来越理解用户
- 在任务中积累经验

那记忆就必须成为核心层，而不是附属功能。

对这个产品来说，记忆不是“把历史消息存起来”，而是“让下一次任务做得更准、更快、更像这个用户要的样子”。

## 2. 这份文档到底要解决什么

这份文档要把 6 件事说清楚：

1. 什么东西应该被记住
2. 什么东西不该被记住
3. 什么时候写入记忆
4. 写到哪一层记忆
5. 什么时候检索记忆
6. 检索出来以后如何影响任务执行

如果这 6 件事不清楚，最后就会退化成“消息归档系统”，而不是“记忆系统”。

## 3. 记忆的基本原则

1. `原始消息不等于记忆`
2. `任务过程要提炼，不要原样堆积`
3. `短期和长期必须分层`
4. `用户记忆和工作记忆不能混成一锅`
5. `只有会影响未来决策的内容，才值得沉淀`
6. `记忆必须可修正、可过期、可升级`

## 4. 四层记忆模型

### 4.1 总览表

| 记忆层 | 作用 | 典型内容 | 写入时机 | 保留时长 | 谁最常读它 |
| --- | --- | --- | --- | --- | --- |
| 工作记忆 | 支撑当前任务推进 | 当前目标、状态、阻塞、待确认项、产物 | 任务开始到完成全过程 | 短期，任务结束后衰减 | Companion、Review Sheet、Agent 执行器 |
| 用户记忆 | 让 Agent 越来越懂这个用户 | 偏好、表达习惯、工作方式、风险阈值 | 发现稳定模式时 | 长期 | Agent 执行器、Companion |
| 环境记忆 | 提升执行效率 | 常用项目、设备环境、工具链、常见上下文 | 环境变化或高频重复时 | 中长期 | Agent 执行器、Connector / Runtime |
| 反思记忆 | 提升未来同类任务质量 | 成功策略、失败模式、复盘结论 | 任务结束后 | 长期，但可被更新 | Agent 执行器、Review / Planning |

### 4.2 工作记忆

工作记忆服务当前任务。

它不是“聊天历史摘要”，而是一个随任务推进不断变化的工作面。

它至少应该包含：

- 当前任务目标
- 当前状态
- 当前阶段
- 最近关键进展
- 当前阻塞点
- 当前待确认事项
- 当前关联文件 / 文档 / 结果物
- 当前使用过的关键上下文

一个很具体的例子：

用户说：“帮我把这周的招聘 pipeline 整理成一个 review。”

工作记忆里不该只存“用户说了一句话”，而应该很快转成：

- 目标：整理招聘 pipeline review
- 当前阶段：收集材料
- 已知上下文：本周会议纪要、候选人表、面试反馈
- 当前阻塞：缺技术面反馈汇总
- 待确认：最终输出是一页总结还是完整文档

这是离前台最近的一层，也是 Companion 最该读的记忆。

### 4.3 用户记忆

用户记忆服务长期个性化。

它应该回答的是：

- 这个人平时喜欢怎样工作
- 他说话常省略什么
- 这个人做决定时最看重什么
- 哪些表达习惯是稳定的
- 哪些风险必须先问清楚

典型内容包括：

- 输出偏好：喜欢中文、先给结论、少废话、要表格
- 工作方式：喜欢异步 review，不喜欢同步盯过程
- 决策习惯：涉及删除、支付、发送前必须确认
- 个人事实：养猫、喜欢陪伴式产品、偏好极简交互

这层记忆必须满足两个条件才值得写入：

1. 是稳定偏好，而不是一次性情绪
2. 它会影响未来任务执行方式

### 4.4 环境记忆

环境记忆服务执行效率。

它主要让 Agent 少问已经知道的问题。

典型内容包括：

- 用户常用项目路径
- 常用仓库和工作目录
- 常用运行时、模型和工具
- 常用设备
- 常用入口
- 经常重复出现的工作场景

举例：

- 这台 Mac 是主工作机
- 常用仓库在 `/Users/caijinhong/Desktop/MyProject`
- 主要工作是产品设计与代码实现并行推进
- 主要移动端是 iPhone 真机，不是模拟器

这层记忆的好处不是“更懂用户”，而是“更少重复配置、更少重复问答、更快进入工作状态”。

### 4.5 反思记忆

反思记忆服务“越做越会做”。

它主要沉淀任务完成后的复盘：

- 这类任务什么做法更稳
- 哪一步最容易出错
- 用户最关心哪类输出
- 哪些上下文必须先拿到

举例：

- 做产品文档重构时，用户不喜欢太抽象的说明，更需要状态表和勾选清单
- 涉及移动端语音调试时，单看实现不够，必须把日志与产品体验放在一起判断

这层记忆会直接影响下一次同类任务的默认做法。

## 5. 什么东西该写进记忆

### 5.1 应该写入的

- 稳定偏好
- 长期事实
- 任务阶段和关键状态
- 任务关键结果
- review / approval 决策
- 复盘出来的可复用经验
- 高频环境信息

### 5.2 不该直接写入的

- 每一条原始消息
- 每一条工具输出
- 每一个中间日志
- 一次性的情绪表达
- 没有复用价值的临时细节
- 敏感信息原文

一句话原则：

`会影响未来行为的，才值得沉淀。`

## 6. 记忆对象模型

第一版建议把记忆对象统一成这种结构：

| 字段 | 含义 |
| --- | --- |
| `memory_id` | 记忆唯一标识 |
| `layer` | 工作 / 用户 / 环境 / 反思 |
| `subject` | 这条记忆是关于谁或什么 |
| `summary` | 一句话可读摘要 |
| `details` | 结构化或半结构化内容 |
| `source` | 来自任务、review、tool、channel、voice 等 |
| `confidence` | 可信度 |
| `stability` | 是临时、阶段性还是长期稳定 |
| `last_verified_at` | 最近一次确认时间 |
| `expires_at` | 是否会过期 |
| `tags` | 检索标签 |

这里最关键的不是字段多，而是两个字段：

- `confidence`
- `stability`

没有这两个字段，系统就会把不稳定的东西误当成长期事实。

## 7. 记忆写入机制

### 7.1 写入不是一次动作，而是 3 段流水线

#### 第一步：capture

先记录原始来源。

来源可能包括：

- 用户输入
- 任务状态变化
- review / approval
- runtime 结果
- 任务完成总结

#### 第二步：extract

从原始来源中提炼出候选记忆。

提炼时必须判断：

- 这是事实还是建议
- 这是稳定偏好还是一次性选择
- 这是短期状态还是长期知识

#### 第三步：promote

把候选记忆写入对应记忆层。

只有通过 promote 的内容，才进入正式记忆。

### 7.2 典型写入时机

| 时机 | 应写入什么 | 目标层 |
| --- | --- | --- |
| 用户交代任务 | 目标、约束、输入上下文 | 工作记忆 |
| 任务进入新阶段 | 当前阶段、进度、阻塞 | 工作记忆 |
| 用户做关键确认 | 决策结果、审批偏好 | 工作记忆 / 用户记忆 |
| 任务完成 | 结果摘要、产物引用 | 工作记忆 / 反思记忆 |
| 出现稳定模式 | 输出偏好、工作习惯 | 用户记忆 |
| 频繁重复环境信息 | 项目路径、工具环境 | 环境记忆 |

## 8. 记忆检索机制

记忆不是“想起来再搜一下”，而应该有固定检索时机。

### 8.1 任务创建时

要检索：

- 用户偏好
- 最近相关工作记忆
- 相关反思记忆

目的是：

- 从第一步就减少误判

### 8.2 任务执行中

要检索：

- 当前工作记忆
- 当前环境记忆

目的是：

- 少重复问
- 少丢上下文

### 8.3 需要 review / approval 时

要检索：

- 用户决策偏好
- 这类任务过去常见风险

目的是：

- 更准确地组织 review 面板

### 8.4 新任务开始时

要检索：

- 过去同类任务的反思记忆

目的是：

- 复用经验，而不是重新试错

## 9. 记忆维护机制

一个能长期使用的记忆系统，必须能做维护。

### 9.1 去重

避免同一条偏好被写很多遍。

### 9.2 升级

例如：

- “这次他说要中文” 不能直接升级成长期偏好
- 但连续 5 次都要求中文，就应该升级为稳定偏好

### 9.3 过期

工作记忆一定会过期。

环境记忆和用户记忆也可能过期，比如：

- 项目路径变了
- 设备换了
- 用户偏好变了

### 9.4 修正

用户说“以后不要这样了”，这不应该只是新消息，而应该修正旧记忆。

## 10. 一个完整例子

### 场景

用户说：

“帮我把 AgentHub 重新整理成一个 companion-first 的产品文档，重点把记忆和 roadmap 写详细。”

### 10.1 当场进入工作记忆的

- 当前任务：重构产品文档
- 当前重点：companion-first、memory、roadmap
- 输出要求：不要太抽象，要具体
- 当前阶段：文档重建

### 10.2 候选用户记忆

- 用户不喜欢过于抽象的产品文档
- 用户希望 roadmap 有打勾表和状态表

### 10.3 候选反思记忆

- 产品文档需要同时有高层方向和执行表，否则不够可用

### 10.4 最终沉淀后的长期记忆

- 输出偏好：要详细、不要只提原则
- 工作偏好：喜欢从整体产品结构重新审视，而不是只围绕单点功能修补

## 12. MVP 顺序

第一阶段建议只先做两层：

1. 工作记忆
2. 用户记忆

原因：

- 这两层最直接影响任务完成率和用户体感

环境记忆和反思记忆可以在第二阶段增强。

## 13. MVP 验收标准

第一版记忆系统至少要满足：

1. 任务中断后能恢复上下文
2. Agent 知道当前任务做到哪
3. 用户的稳定偏好能影响下一次执行
4. review / approval 会影响后续做法
5. 任务完成后会沉淀一条可复用经验
