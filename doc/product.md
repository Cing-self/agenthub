# AgentHub 产品定义

## 1. 产品一句话

AgentHub 是一个 `companion-first` 的 Agent 产品。

用户平时面对的不是一个大聊天窗口，而是一个常驻桌面的陪伴式入口。用户通过文字、语音、文档、视频等方式交代任务，Agent 在后台持续执行，只在需要确认、遇到阻塞或完成任务时主动唤起用户。

## 2. 产品目标

产品最终要同时满足 4 件事：

1. `能干活`
   用户交代任务后，Agent 不是只会聊天，而是真正去执行。
2. `能异步`
   用户不需要一直盯着界面，过一段时间再回来审查也成立。
3. `能沉淀`
   任务过程、结果和经验会进入记忆，而不是每次重新开始。
4. `有陪伴感`
   用户感受到的是一个温暖的桌面伙伴，而不是一个冷冰冰的控制台。

## 3. 核心产品形态

产品由三层组成：

### 3.1 前台 Companion

这是用户默认看到的产品。

它应该：

- 常驻桌面
- 有陪伴感和轻状态反馈
- 支持快捷键唤起
- 接收任务输入
- 在关键时刻提醒用户

它不应该：

- 长期占据大窗口
- 暴露复杂配置
- 把大量消息历史当作主界面

### 3.2 Review Sheet

这是用户最常用的展开层。

它应该快速回答：

- 现在在做什么
- 做到了哪一步
- 需要我决定什么
- 已经产出了什么

它是 `review-first`，不是 `chat-first`。

### 3.3 Console

这是后台操作台。

它服务于：

- 高级用户
- 配置场景
- 调试场景
- 深度审查场景

现在仓库里的桌面 App 主要是这层。

## 4. 用户主循环

AgentHub 未来的主循环应该是：

1. 用户交代任务
2. Agent 开始执行
3. Agent 在后台推进
4. 需要用户时主动唤起
5. 用户确认、改方向或补上下文
6. Agent 完成并给出结果
7. 结果和经验沉淀为记忆

这里的核心对象不是“聊天消息”，而是“任务生命周期”。

## 5. 输入不是产品，任务才是产品

文字、语音、文档、视频都只是输入形式。

它们最终都应该进入同一个内部模型：

- 用户要做什么
- 给了哪些上下文
- 有什么约束
- 什么时候需要确认

所以未来产品不应该做成：

- 文本产品
- 语音产品
- 视频产品

而应该做成：

- 一个统一任务入口
- 多模态只是输入和补充上下文

## 6. 产品原则

1. `前台轻，后台重`
   用户看到的是轻入口，复杂系统藏在后面。
2. `任务优先，不是聊天优先`
   聊天只是手段，不是主界面。
3. `异步优先`
   用户不需要全程盯着 Agent。
4. `记忆优先`
   越用越懂用户，是产品核心价值。
5. `陪伴感优先于工具感`
   先让用户觉得它在身边，再让用户意识到它很能干。
6. `个性化比通用 IP 更重要`
   最有温度的 companion，通常是用户已有情感连接的对象。

## 7. 个性化 Companion

Companion 不应该被写死成唯一官方形象。

更合理的方向是：

- Agent 核心保持稳定
- Companion 外观和表达可替换
- 用户可以选择更有情感连接的形象

例如：

- 官方猫咪
- 极简精灵
- 用户自己的宠物化身

对用户来说，它始终是“同一个伙伴”；对系统来说，外观和能力是分层的。

## 8. 明确不做什么

当前阶段不应该把产品继续推向：

- 一个越来越重的桌面聊天软件
- 一个把所有内部状态都暴露给用户的大控制台
- 一个只会聊天、不会持续执行任务的 Agent 外壳
- 一个只靠堆消息记录来假装有记忆的系统
